## 分层模型

用固定方向的分层模型，避免 agent 临场发明架构：

`Types -> Config -> Repo -> Service -> Runtime -> UI`

前端项目默认链：`shared -> components -> pages`（需要时再引入 `features` / `widgets`，别提前建层）。链可以按项目换，**方向规则不变**：低层不知道上层存在。

跨领域关注点应该通过明确的 provider 或 adapter 边界进入，而不是直接跨层穿透。

## 硬性依赖规则

- 低层不能依赖高层。
- UI 不能绕过 runtime 或 service 契约。
- 数据访问必须通过 repo 或等价 adapter 进入。
- 展示用文案集中在一处（例如 `src/shared/text.ts`），组件里不写第二套说法。
- 共享 util 必须保持通用，不能慢慢堆成领域逻辑垃圾桶。
- 新依赖要在对应 plan 或 design doc 里说明理由。

## 工程约定

新项目按实际栈改写这一节，建议保持以下结构：

- **栈**：`[语言 / 框架 / 构建工具版本，Node 版本要求]`
- **样式**：`[方案]`；设计 token 集中在一个文件（色板 / 字体 / 间距），组件里不写魔法色值；类名语义化、保持低特异度，别和 UI 库的 CSS-in-JS 互相抵消；要盖过库样式就限定作用域，不用 `!important`。
- **命名与拆分**：文件 kebab-case，组件 PascalCase，hooks `use` 前缀；一个文件一个主职责，软上限约 300 行，超了就拆。
- **测试**：测试就近放（`*.test.ts[x]`），只保留一种位置约定；纯逻辑必须有单测，UI 至少覆盖"关键结论先出现、主交互生效"。
- **UI 验证**：改 UI 必须真的渲染过（自动化断言 + 手动看一眼），不能只读代码宣布完成。
- **数据与校验**：数据格式的约定写进文档，并配一个守卫测试防止漂移。
- **提交信息**：`<type>: <短描述>`，type ∈ feat / fix / docs / refactor / chore / test / perf。

## 变更检查

当你修改了会影响架构的代码：

1. 如果领域地图或允许边界变了，就更新这份文件。
2. 如果背后的设计理由变了，就更新 `docs/design-docs/` 里的相关文档。
3. 如果规则应该机械执行，就补一个测试或检查。
