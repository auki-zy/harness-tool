# TESTING.md

这份文件定义测试策略：每个改动该写什么测试、写到什么程度、何时算通过。测试是行为的**证据**，不是 CI 的装饰（呼应 `AGENTS.md` 完成定义与 `QUALITY_SCORE.md` 的"测试稳定性"）。
配套：`CODE_STANDARDS.md`（命名/拆分）、`CI_CD.md`（门禁）、`BOOTSTRAP.md`（框架安装）。

## 测试层级（金字塔）

| 层级 | 测什么 | 放哪/命名 | 倾向 |
|------|--------|----------|------|
| 单元测试 | 纯逻辑、utils、hooks、reducer、model 层 | 就近 `*.test.ts` | 多，快，密 |
| 组件测试 | 组件渲染/交互/状态（Testing Library） | 就近 `*.test.tsx` | 中 |
| 集成测试 | 切片内 ui+model+api 协作（mock 掉网络） | 就近或 `__integration__/` | 少而关键 |
| E2E（可选） | 黄金旅程跨页流程 | `e2e/`（bootstrap 定框架） | 极少，护核心路径 |

- **行为优先**：断言用户可见行为与状态，不断言实现细节（不脆测内部函数调用顺序）。
- 一个文件一个主职责的测试就近放置；命名与目录规则见 `CODE_STANDARDS.md`（`*.test.ts(x)` 与 `__tests__/` 只能选一种，禁混用）。

## mock 边界规则

- mock **外部边界**（网络、时间、浏览器 API、第三方库），**不 mock 自己代码内部**——否则测的是假实现。
- 网络请求统一走 api 层封装后 mock 该层；组件测试里尽量不 mock 子组件（除非真的慢/重）。
- 过度 mock 导致"全绿但一改就碎"是坏味道：优先重构可测性（纯函数提取），而不是加 mock。

## 覆盖率与门禁

- 行覆盖率作为**下限**而非目标（建议起点 70–80%，bootstrap 时定值）；关键路径（auth、支付、数据写入）必须显式列清单覆盖。
- 新增/修改逻辑必须有对应测试改动，禁止"删测试让红变绿"。
- 测试进 CI 门禁（见 `CI_CD.md`）：红 = 阻断合并，先修 baseline 再加新范围。

## UI 验证证据

- 组件行为改动：组件测试为主；**视觉/布局改动必须留截图或浏览器实测证据**（挂到 plan，呼应 `FRONTEND.md` UI 验证闭环）。
- 可访问性断言（`jest-axe` 等）加入组件测试默认项（呼应 `FRONTEND.md` a11y 清单）。

## 失败处理

1. 红 → 修实现或修错误断言 → 绿。
2. flaky 测试：禁止无限重试掩盖；标记 `@flaky` 并当轮修或记录 tech-debt（`tech-debt-tracker.md`），给修复时限。
3. 测试成为维护负担时，先重构可测性，再谈删测试。
