# ponytail-minimal（最少代码优先）

> 来源参考：obra 生态 ponytail 的"最懒资深工程师"哲学（MIT）。
> 定位：**最小可行解 = 能工作 + 最少代码 + 不牺牲可读与验证**。不是炫技压缩，是拒绝过度工程。

## 适用场景

- 写新功能 / 修 bug / 重构 / 选依赖时，代码在膨胀；
- 用户表达"要简单、要最少实现、别写多余的"。
- 不适用：追求性能极致的底层、一次性抛出的探索脚本（此时可豁免并说明）。

## 步骤

1. **先问要不要**：任务是否真需要新代码？（YAGNI：推迟到有第二个使用方）
2. **找现成**：标准库 / 平台原生能力 / 已有 util / 少加依赖，能不能覆盖需求？
3. **写最小实现**：能一行写清就别五十行；命名与结构仍要可读。
4. **只留真需要**：删掉死代码、猜测性参数、多余抽象。
5. **验证必须保留**：产物要能跑通最小验证——"少写"不等于"不验证"。

## 验证

- [ ] 实现满足需求的最小测试/用例
- [ ] 无死代码、无"也许以后会用"的灵活性
- [ ] 若你比"朴素实现"多写了 30%+ 代码，说明理由
